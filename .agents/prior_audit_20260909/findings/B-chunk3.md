## Findings

### B-3-01: `validate_output.py`'s expected-column list is stale — missing 3 of the real output schema's columns, so the validator can't catch problems in them

- **Doc/claim**: `test-bed/src/Modules/robust_testing/kradar/scripts/validate_output.py:5-10` (module docstring) — "this script checks: ... b. Every column in the expected_cols list is present. ... d. ghost_flag column has boolean dtype." The script positions itself as the schema-completeness/sanity check for the pipeline's Parquet output.
- **Code**: `validate_output.py:33-42` — `expected_cols` includes `ghost_flag` but omits `lidar64_visible_confirmed`, `lidar128_visible_confirmed`, and `occluded`. Cross-referenced against `config.OUTPUT_SCHEMA` (`src/kradar_visibility/config.py:110-161`, 46 entries) and `pipeline.py` (which actually populates `lidar64_visible_confirmed` at ~370/486, `lidar128_visible_confirmed` at ~371/490, `occluded` at ~521 — per chunk 1 finding B-1-03, already established these 3 real columns plus `ghost_flag` are undocumented in architecture.md; `ghost_flag` alone made it into this validator's list, the other 3 did not).
- **Contradiction**: the validator's whole purpose is to catch schema drift/missing columns/wrong dtypes in the Parquet output before it's used downstream. Because `lidar64_visible_confirmed`, `lidar128_visible_confirmed`, and `occluded` aren't in `expected_cols`, `validate_output.py <path>` would report a clean PASS on a Parquet file that is missing those 3 columns entirely, or that has them at the wrong dtype (they're never dtype-checked, and `occluded`/the two `*_confirmed` columns aren't `_score`-suffixed so rule (e)'s `[0,1]` range check never touches them either since they're boolean, not float — but the point stands that presence/dtype is silently unchecked for 3 real columns).
- **Severity**: doc-drift (the script's own claim to validate "every column" and the schema it validates against are both stale relative to the real schema — a coverage gap in a tool whose entire job is coverage).
