### A-2-01: No test exercises `pipeline.compute_visibility_for_frame`/`run()` with a missing radar cube — the A-1-01 bug (radar_visible not gated on cube presence) has zero test coverage

- **File:line**: `test-bed/src/Modules/robust_testing/kradar/tests/test_smoke.py` and `tests/test_verify.py` (whole files)
- **Mechanism**: `grep -n "compute_visibility_for_frame" tests/test_smoke.py tests/test_verify.py` returns no matches — neither file ever calls `pipeline.compute_visibility_for_frame()` or `pipeline.run()`. The closest related test, `test_ver01_r_implies_radar_visible` (test_verify.py:19-25, re-asserted at line 367-373 as `test_ver01_r_implies_radar_visible_still_works`), only checks the one-directional implication `sensor_identify contains 'R' -> radar_visible True` on whatever `output_table` fixture already produced — it never constructs a frame where `radar_zyx_cube/cube_{frame_idx}.mat` is absent and an object is geometrically inside the FOV/range cone, which is exactly the scenario A-1-01 identified as producing a false `radar_visible=True`.
- **Failure scenario**: this is a coverage-gap finding, not a runtime failure — the concrete consequence is that A-1-01 could ship silently, since running the full existing test suite (`uv run pytest tests/test_smoke.py tests/test_verify.py`) would not fail even with the bug present, because no test drives the missing-cube path through the pipeline layer (only `data_loader.load_radar_cube` returning `None` is smoke-tested in isolation at test_smoke.py:97-99, never wired through to `radar_visible`).
- **Severity**: doc-drift (test suite's documented purpose — "verification tests," VER-01 docstring claiming to check `radar_visible` correctness — does not match what it actually verifies; the gap is what let A-1-01 through, but the test file itself isn't wrong code, it's incomplete coverage against its own stated intent).

### A-2-02: `test_ver27_lidar_score_with_range_image`/`test_ver28_.../test_ver29_...` use `expected_density=10.0`, a value that only ever exercises the OS2_64_CHANNEL_LUT branch of the broken `expected_density > 50` heuristic — the real OS2-64/OS1-128 values (8000/32000, both >50) are never tested, so A-1-02 has zero coverage under real-world inputs

- **File:line**: `test-bed/src/Modules/robust_testing/kradar/tests/test_verify.py:78, 117, 179` (class `TestLidarWithRangeImage`, VER-27/28/29)
- **Mechanism**: all three tests in this class hardcode `expected_density = 10.0`. Line 179's comment reads verbatim: `expected_density = 10.0  # <=50 -> calculate_lidar_visibility selects OS2_64_CHANNEL_LUT` — the test author was aware of and specifically targeting the `> 50` threshold in `lidar_visibility.py:185-195` (per A-1-02), but only tested the branch reachable with a synthetic small `expected_density`. The real values computed in `pipeline.py` (`_EXPECTED_OS2=8000.0`, `_EXPECTED_OS1=32000.0`, both far above 50) are never passed to `calculate_lidar_visibility` in any test in this file.
- **Failure scenario**: because the tests use `expected_density=10.0` (<=50), they always correctly hit `OS2_64_CHANNEL_LUT` and pass — giving false confidence that channel-LUT selection is correct, when in production (`expected_density` computed from real sensor specs) the same code path always misfires per A-1-02. Repro: `uv run pytest tests/test_verify.py::TestLidarWithRangeImage -v` would pass today despite A-1-02 being live in production data, because the test's own density value sidesteps the broken threshold rather than testing it under realistic conditions.
- **Severity**: silent wrong output (the test suite actively demonstrates awareness of the `>50` threshold's existence yet never validates it against real sensor `expected_density` magnitudes, which is how a threshold bug ships and stays hidden).
