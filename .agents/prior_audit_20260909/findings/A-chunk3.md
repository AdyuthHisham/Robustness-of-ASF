## Findings

### A-3-01: `validate_precomputation.py` cannot catch the A-1-01 bug — it reimplements the identical buggy formula and never compares against pipeline output

- **File:line**: `test-bed/src/Modules/robust_testing/kradar/scripts/validate_precomputation.py:281-297` (recomputation) and `:358-363` (comparison logic).
- **Mechanism**: This script's stated job is to recompute visibility from precomputed products and validate it against `compute_visibility_for_frame()`'s output (called at line 266 as "the reference output"). But at line 284 it independently recomputes `radar_visible = radar_fov_in and radar_range_in` — the exact same formula as the buggy one in `pipeline.py` (A-1-01), with no dependency on `radar_cube is not None` either. Then at line 358 the script's own comment reads: `# Compare with pipeline output (optional: we could assert equality, but for validation we just check they are computed)` — followed only by range asserts (`0.0 <= radar_score <= 1.0`, etc., lines 360-363). There is no equality/mismatch assertion between the recomputed `radar_visible`/scores and the pipeline's actual output row (`frame_rows` from line 266) anywhere in the file.
- **Failure scenario**: even with a missing radar cube where A-1-01 fires (pipeline emits `radar_visible=True` incorrectly), this validator recomputes the same wrong `radar_visible=True` locally via the identical formula, and even if it didn't, it never diffs against the pipeline's real output — so `uv run python scripts/validate_precomputation.py` (or however it's invoked) would report success regardless of whether A-1-01 is present or fixed. The script's name and stated purpose ("validate precomputation... against reference output") is not what the code does for radar visibility.
- **Severity**: silent wrong output (a script whose job is specifically to catch this class of bug cannot, by construction, catch it).
