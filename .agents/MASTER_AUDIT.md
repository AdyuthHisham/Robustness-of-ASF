**A-1-02** — `radar_visibility.py:271-275` and `radar_visibility.py:289-293`
```python
nf_subset = noise_floor_db[bbox['z_min']:bbox['z_max'], bbox['y_min']:bbox['y_max'], bbox['x_min']:bbox['x_max']]
...
subset_db = cube_db[bbox['z_min']:bbox['z_max'], bbox['y_min']:bbox['y_max'], bbox['x_min']:bbox['x_max']]
```
`bbox['z_max']/'y_max'/'x_max'` come from `pipeline.py:_bbox_voxels_from_annotation()` (`pipeline.py:143-160`) as `max(vz)` etc. — an **inclusive** voxel index (the actual last corner voxel of the object). Slicing with Python's exclusive-upper-bound semantics (`z_min:z_max`) drops the entire last voxel plane in every one of the 3 dimensions from both the noise-floor subset and the signal subset used to compute the SNR score. Repro: for `bbox = {'z_min':10,'z_max':10,...}` (plausible for small objects near the ~0.4 m Z voxel pitch given `RADAR_GRID_Z=150` over 60 m), `cube_db[10:10, ...]` is an empty slice; combined with the `pipeline.py:309-311` guard (`bbox['z_max'] > bbox['z_min']`), such objects are skipped entirely and `radar_score` stays at its `0.0` default even though the object physically occupies that voxel. For larger boxes, every computed score systematically excludes the outer max-index voxel layer in each axis, biasing every non-degenerate `radar_sparsity_score` low. Correct code should slice `z_min:z_max+1` (etc.) given how `z_max` is produced.
Severity: silent wrong output (affects every `radar_sparsity_score` value in the output table, and drops some small objects to `radar_score=0.0`/`radar_visible` mis-scored entirely).

**A-1-03** — `lidar_visibility.py:184-206`
```python
if expected_density > 0:
    if expected_density > 50:  # Arbitrary threshold - OS1-128 has higher density
        channel_lut = OS1_128_CHANNEL_LUT
    else:
        channel_lut = OS2_64_CHANNEL_LUT
```
`calculate_lidar_visibility()` guesses which channel LUT (64 vs 128 channels) to use for the range-image occlusion check from `expected_density` instead of being told directly which sensor it is scoring. `pipeline.py` computes `_EXPECTED_OS2 = (64 * 22.5/360) * (360/0.18) = 8000.0` and `_EXPECTED_OS1 = (128 * 45/360) * (360/0.18) = 32000.0` (`pipeline.py:80-81`). Both are `> 50`, so the OS2-64 call (`pipeline.py:334-340`, `expected_density=_EXPECTED_OS2`) always selects `OS1_128_CHANNEL_LUT` (128 channels) even though it was given `os2_range_image` (shape `(64, azimuth_bins)`). `_validate_range_image_dimensions()` (`lidar_visibility.py:223-236`) then compares `range_image.shape[0] == 128` against the real shape `64` → `False` → falls back to `occluded_fraction=0.0, confidence=0.0` (`lidar_visibility.py:198-201`). Since `final_score = density_ratio * (1.0 - occluded_fraction * confidence)` (`lidar_visibility.py:213`), `confidence=0.0` zeroes the occlusion term regardless of true occlusion, so `final_score == density_ratio` unconditionally for every OS2-64 (lidar64) object — the range-image occlusion-aware scoring the module docstring claims as new ("Added support for precomputed range image to compute occlusion fraction") is silently a no-op for `lidar64_sparsity_score` in every row ever produced (OS1-128 routes correctly by accident, since `32000 > 50` happens to pick the correct LUT).
Severity: silent wrong output — a documented feature (lidar64 occlusion discount) is dead in practice; every `lidar64_sparsity_score` reduces to `points_count / expected_density`.

**A-1-04** — `pipeline.py:297` (`for obj in objects:`)
Per AGENTS.md:54-56: "Vectorize per-frame, per-object computation... radar/LiDAR/camera scores must scale across all objects in a frame, not loop per-object in pure Python." `compute_visibility_for_frame` loops over every object in pure Python and, inside that loop, calls `calculate_lidar_visibility(os2_points, bbox_list, ...)` (line 334) and `calculate_lidar_visibility(os1_points, bbox_list, ...)` (line 352) where `bbox_list = [_bbox_list_from_annotation(obj)]` (line 327) is always a **single**-object list. `calculate_lidar_visibility` supports batched `bboxes` internally (`for i, bbox in enumerate(bboxes)`, `lidar_visibility.py:154`) but is always invoked with `n=1`, so the batch-capable interface never actually batches across a frame's objects — vectorization the function was written to support is unreachable from its only call site. Camera scoring (`calculate_camera_visibility`, called once per object at `pipeline.py:402`) likewise repeats its 4-direction × 2-stereo-subcam calibration lookups and projections per single object.
Severity: perf/architecture violation — for a frame with N objects, the radar/lidar/camera scoring machinery (including calibration lookups, see A-1-05) reruns N times instead of once vectorized across N objects, as AGENTS.md explicitly requires.

**A-1-05** — `calibration.py:40-45` (`load_camera_calibration`), used by `calibration.py:47-61` (`get_camera_params`), called from `camera_visibility.py:205` and again from `pipeline.py:419`
`load_camera_calibration()` does an unconditional `pickle.load()` of the full `T_params_seq/{seq}` calibration file on every call, with no caching. `get_camera_params(direction, seq)` calls it once per direction. Inside the per-object loop, `calculate_camera_visibility()` (`pipeline.py:402`) calls `get_camera_params()` once per direction (4×) to score, then, for every direction found visible, `pipeline.py:419` calls `get_camera_params(direction, seq=seq_int)` **again** to get projection params for `cam_*_proj_x/y`. For a frame with N objects, this is up to `N × 4 × 2 = 8N` full pickle-file loads of the calibration data per frame, where 1 load per sequence would suffice since calibration is static per `seq`.
Severity: perf bug — repro-able, quantifiable, avoidable O(N) I/O blowup per frame, compounding A-1-04's per-object-loop violation of AGENTS.md's vectorization rule.

**A-1-06** — `pipeline.py:39-52` (imports)
`data_loader.load_camera_image` is never imported or called anywhere in `pipeline.py` (the import block at lines 39-52 imports `load_radar_cube, load_lidar_points` from `data_loader` but not `load_camera_image`).
