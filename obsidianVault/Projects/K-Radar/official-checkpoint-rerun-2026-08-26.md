update: the original 58-sequence corruption sweep used a self-trained checkpoint
(`exp_260506_135737_A2FUSION_.../model_10.pt`, MD5 `805ac29a...`) instead of the official

## Bugs found and fixed this session

1. **Login-node Python too old.** Alvis's bare `python3` is 3.6.8, predates
   `from __future__ import annotations` used by `merge_predictions_text.py` → crashed the whole
   batch driver via `set -e` after batch 1's ~340 GPU jobs had already run (no data lost, but
   the driver stopped). Fixed by `module load Python/3.11.3-GCCcore-12.3.0` before invoking it,
   and moved the merge step off the login node entirely into a CPU-only Slurm job
   (`scripts/alvis/merge_batch.sbatch`, `-C NOGPU`) per user direction.
2. **`sbatch --export` comma-truncation — caused real data loss.** `merge_predictions_text.py`
   gained a `--seqs` filter to scope a batch's merge to exactly its own sequences (otherwise
   not-yet-deleted raw dumps from other sequences/batches get silently folded in). The batch
   driver passed this as `--export=ALL,...,SEQS=1,2,3,...,10` — but `sbatch --export`'s own
   syntax uses commas to delimit `NAME=VALUE` pairs, so `SEQS` silently truncated to `SEQS=1`.
   The merge job only ever processed sequence 1; the driver then deleted all 10 sequences' raw
   dumps believing the merge had covered all of them. **Sequences 2–7's raw per-frame dumps for
   that corruption-sweep batch were permanently lost** (sequences 8–10 were caught in time and
   killed before deletion reached them; sequence 1 survived by the bug's specific failure mode).
   Fixed by switching `--seqs` to a `+`-delimited value (comma-safe inside `sbatch --export`),
   `merge_predictions_text.py` now refuses outright if `--seqs` contains a comma, and
   `run_batched_sweep.sh` gained a hard gate that verifies the merge log's `Found N sequence
   directories` count matches the batch size before any raw dump is deleted.

## Baseline mAP (pooled across all 58 sequences, 13,727 frames, `original` condition)

Computed two independent ways, cross-validated:

1. **Reused pipeline**: `ingest.py` (IoU-threshold-scoped IoU matching, one pass per threshold
   since the threshold is baked into TP/FP determination, not post-hoc) → `ap_metrics.py`'s
   pooled 41-point AP, same code `radar_charts.py` already uses.
2. **K-Radar's own official evaluator** (`utils/kitti_eval/eval_revised.py`, run by the user via
   `compute_complete_results_standalone.py` against the full official test split — same 13,727
   frame count).

| Class | Metric | IoU 0.7 | IoU 0.5 | IoU 0.3 |
|---|---|---|---|---|
| Sedan | AP, mine (pooled BEV) | 43.25 | 71.71 | 77.86 |
| Sedan | AP, official (BEV) | 43.25 | 71.71 | 77.86 |
| Sedan | AP, official (**3D**) | 11.86 | 52.15 | 74.99 |
| Bus | AP, mine (pooled BEV) | 20.89 | 53.22 | 67.93 |
| Bus | AP, official (BEV) | 20.90 | 53.21 | 67.93 |
| Bus | AP, official (**3D**) | 7.95 | 31.02 | 58.15 |

BEV numbers agree between the two independent implementations to within ~0.01 — strong
correctness signal for both `ap_metrics.py` and the ingest/matching pipeline. 3D AP is
meaningfully lower than BEV at higher IoU (expected: 3D IoU also penalizes height/z-position
error that BEV ignores) — the more rigorous number if full 3D localization quality matters, not
just ground-plane footprint. Official eval also reports 2D-bbox and AOS AP, both **not
meaningful** here — K-Radar hardcodes a dummy 2D bbox (`50 50 150 150`) for every object (see
[[asf-map-eval-mechanics]]), so those columns just reflect that dummy box.

Internal consistency check: `num_gt` (29,613 sedan + 5,843 bus = 35,456) exactly matches the
merge's total GT line count, identical across all three IoU thresholds as expected (GT count is
threshold-independent; only TP/FP split changes).
