# 2026-09-03

## Phase 2: empirically confirmed the LiDAR-Gaussian-noise mechanism via CPU forward pass

Continuation of yesterday's Phase 1 audit ([[asf-availability-told-not-aware]],
`docs/vAIlt/06_Results/lidar-gaussian-noise-mechanism-phase1-audit-20260902.md`).
User confirmed Alvis storage mounts (data/pretrained/etc.) still work for reads —
no CPU/GPU nodes remain on Alvis, so any forward pass has to run locally
([[project_alvis_permanently_unavailable]] updated to reflect this nuance).

Ran the scoped Phase 2 hook: 5 paired clean/`lidar_gaussian_noise_high` frames
(seq 32), single-frame no-grad CPU forward passes, dumping `feat_indiv`/
`fused_feat`. Got there after a long chain of CPU-porting fixes, all in a
standalone script — spconv's CPU build doesn't support fused act+bias in
`indice_conv` (patched: strip fusion, apply bias/activation manually in plain
torch, exact not approximate); several CUDA-only extensions
(`roiaware_pool3d`, `iou3d_nms`, `pointnet2_stack`, `sort_vertices`,
`bev_pool_ext`) needed stubbing or a plain-torch reimplementation (bev_pool via
`index_add_` — an approximation of the exact CUDA kernel's spatial indexing,
but immaterial since the camera branch it feeds is LiDAR-noise-invariant by
construction, confirmed by the identical camera-feature result below). Also
hit and worked around (not fixed) two real pre-existing repo bugs unrelated to
this investigation: `get_label()` hardcodes a stale label-revision path that
resolves to an empty directory (`tools/revise_label/` vs the real
`tools/revise_label_local/`), and `collate_fn` throws on zero-object frames
(`remove_0_obj=True`, already the config default, is what avoids this —
turning it off to dodge the path bug was the wrong fix, re-enabling it once
the path bug was actually fixed was correct).

Also: mid-session, killing a hung earlier attempt appears to have taken down
all four Alvis sshfs mounts entirely (no `sshfs` process left running) — had
to ask the user to remount before continuing. Worth remembering as a real
failure mode of `kill -9`'ing a process with an in-flight FUSE request.

**Result, 5/5 frames fully consistent**: camera features bit-identical
clean-vs-noisy (sanity check); radar unchanged; LiDAR branch
(`spatial_features_2d`) shows a small, consistent **+4.2–4.5%** increase in
mean activation magnitude, std essentially flat — not chaos, not collapse, a
systematically stronger but still well-behaved feature map; fused output
shows **+2.1–2.6%**, about half the LiDAR shift, exactly consistent with
ungated cross-attention passing the perturbation through proportionally.
Empirically confirms yesterday's code-read finding (no availability/quality
gate exists) rather than just resting on it.

**Honest limit flagged**: a clean global +4% magnitude shift doesn't obviously
explain Stage A's ~4x FN-rate explosion by itself — likely the real damage is
spatial (misaligned anchor cells from scattered points), not magnitude, which
would need a per-cell diff map to confirm directly (scoped, not run). Box-level
(post-NMS) confirmation also not obtained since CPU NMS isn't implemented in
this repo. Two new blocking questions raised for the user: whether to pursue
the spatial diff map, and whether box-level confirmation via a CPU NMS
reimplementation is worth it or the feature-level evidence suffices for the
thesis section.
