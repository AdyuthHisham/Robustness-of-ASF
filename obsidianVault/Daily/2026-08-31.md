(precision/recall/F1, mATE/mASE/mAOE, churn, CRI, anomaly detection) over the
same `full_denormalized_table.parquet`. Ran Phase 1 read-only audit first per
repo convention.

Resolved four questions the user pushed back on / asked to dig deeper on:

- **AP feasibility**: traced `all_preds.txt` → post-NMS `SCORE_THRESH=0.1`
  filter in the model head → confirmed K-Radar's own official benchmark AP
  reads from the same post-filtered predictions, no further score filtering.
  Restricted-range AP isn't a limitation of this analysis specifically — it's
  the standard KITTI protocol, K-Radar included. One loose thread: observed
  score floor is 0.30 not the configured 0.10, cause not found, flagged as
  low-priority caveat.
- **Churn/GT-pairing mechanism**: explained and empirically re-confirmed
  `matched_gt_row_id` stability (35,455 GT objects, 0 collisions across 31
  conditions) — [[gt-transition-analysis]]'s matcher can be called directly.
- **frame_deletion crash-coverage**: confirmed by user as expected/by-design,
  22-condition scope (drop frame_deletion) proceeds as planned.
- **Orientation heading vs. axis**: checked K-Radar's own AOS formula
  (`(1+cos(Δ))/2` in `eval_revised.py`) — cos is full-period, so a 180°-flipped
  box scores 0 similarity, confirming K-Radar treats orientation as a genuine
  heading. mAOE must wrap mod 2π, not mod π.

Full findings: [[exhaustive-crossproduct-phase1-audit]]. Still open before
Phase 2 implementation: whether to report restricted-range AP as a labeled
secondary metric, and the minimum-N reliability floor (30 vs. 100).
