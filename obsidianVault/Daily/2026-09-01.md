## Root-caused the noisy-vs-absent-LiDAR paradox: ASF is availability-*told*, not availability-*aware*

Investigated why `lidar_gaussian_noise_medium/high` (sed AP 11.07/11.23, ~25%
retention) devastates ASF far worse than `lidar_loss_complete_zero` (sed AP 43.38,
58% retention) — the opposite of what a genuinely availability-aware fusion
architecture should produce. Traced to code, not just numbers: ASF's only
availability mechanism is a membership check in `a2_fusion.py:166-173`
(`if temp_key not in batch_dict['avail_feats']: continue`) — populated only by
hand-run demo scripts (`main_fusion_eval_0.py::vis_objects`, `main_get_videos.py`)
using a fixed, externally-chosen `infer_mode` per run, exactly matching the paper's
own Table 3 binary-combination methodology. **`pipelines/pipeline_detection_v1_0.py`'s
`test()`/`validate()` — what this repo's entire 58-sequence sweep actually runs
through — never sets `avail_feats`** (confirmed by grep). So every sweep condition,
including `loss_complete_zero`, runs with all three branches always present in
CASAP's query; `loss_complete_zero` just zero-fills the raw point array
pre-voxelization rather than triggering the skip path.

Mechanistic read: an all-zero point cloud voxelizes to a near-empty grid the
backbone already treats leniently (resembles sparse real scenes); Gaussian noise
at/above voxel scale (σ=0.5-1.0m vs 0.4m voxels) scatters points into a dense,
plausible-looking-but-wrong occupancy pattern that CASAP has no way to distinguish
from real dense returns, so it's trusted at full weight and actively corrupts
fusion rather than being ignored. Sharpens adversarial-review critique #3: ASF has
no failure *detector*, only a failure *declarer* — it needs an oracle to already
know a sensor died before inference. Full writeup:
[[asf-availability-told-not-aware]].

## Two more trends dug out of crossproduct_v2, following the same "check the mechanism" pattern

Chased two items `docs/crossproduct_trends_and_anomalies.md` left as
flagged-but-unresolved. (1) The "13/21 conditions show suspicious recovery" claim

## CRI's "blocked" status was stale — it's directly computable from row_table_iou03.parquet

Ran a metrics-coverage audit against `docs/crossproduct_trends_and_anomalies.md`
(user request). CRI (RoHOI Eq. 2) had been flagged blocked since the 8/31 Phase 1
audit on the grounds that it needs raw per-severity AP from a separate source,
`ap_robustness_local.json` (an older 2-class pilot output), never joined to the
crossproduct pipeline. That reasoning no longer holds: `row_table_iou03.parquet`'s
`condition` column already encodes severity per corruption effect, and
`compute_ap_grouped(row_table, ["condition", "cls"])` — the same helper
`master_metrics_table.py` already uses for mAP/RCE — gives exactly the raw
per-severity AP CRI's formula needs. The blocker was real only before that helper
existed in its current form; nobody revisited the note after the tooling caught up.

Computed CRI for every effect x class currently in the table (sed/bus only — this
row table's own class coverage). Lowest (worst) scores: `lidar_gaussian_noise`
(0.11-0.15, both a huge mean-AP collapse and huge variance). Notable split:
`camera_frame_deletion` scores 0.83 for `sed` but 0.25 for `bus` — same effect,
same modality, opposite outcomes, because `bus` only collapses at `high` severity
while `sed` stays flat, and CRI's variance term catches that where mRR/mAP alone
wouldn't distinguish as clearly. Also flagged an unresolved oddity worth a
follow-up: `radar_frame_deletion` and `lidar_frame_deletion` AP values are nearly
identical across all severities despite being independently-corrupted modalities —
possible shared-artifact in the frame-drop mask, not yet checked against the
9/1 frame-key fix.

Full table and formula detail: [[cri-computed-from-row-table]]. This reverses
another documented-as-blocked item the same way item-1's "AP is not computable"
verdict was reversed earlier today — worth scanning other `docs/vAIlt/`
"blocked"/"limitation" notes for similar staleness.
