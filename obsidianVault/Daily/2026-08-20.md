# 2026-08-20

## ASF corruption sweep: completed all 58 sequences, found and fixed two silent-truncation bugs

Continuation of [[asf-corruption-study-alvis]] — resumed the file-count-quota-blocked sweep
(project quota at 99% of 5M files), pivoted from a planned Parquet consolidation to a simpler
flat-text merge (`outputs/all_preds.txt` / `all_gts.txt`, tagged `<seq>_<frame>_<condition>`),
reclaimed ~1.22M files by deleting 128 duplicate `exp_*` run dirs plus every already-merged
`test_kitti/` tree, then resubmitted the 40 sequences that had silently ended up with zero
corrupted-condition data (root cause: the same quota wall killing jobs instantly mid-sweep on
2026-08-18) in 4 batches, verifying and merging each one.

Two more silent-completeness bugs surfaced and got fixed along the way, both invisible to
`sacct`/job-log-success checks:

1. **6 sequences (15,16,18,41,48,55) had corrupted-condition data from an 08-17
   frame-limited "spot-check" batch** masquerading as complete (job log showed the dataloader
   itself only exposing 10 samples) — resubmitted full sweeps, had to strip old lines before
   merging since the deterministic seed made old/new predictions byte-identical for
   overlapping frames (would've silently duplicated otherwise).
2. **`asf_run.sbatch` can't detect a mid-run disk-quota crash** — it counts whatever
   prediction files exist after the process exits as "OK," so 5 of seq12's LiDAR conditions
   silently truncated to 31-98% frame coverage while reporting clean `COMPLETED` status.
   Found via `OSError: Disk quota exceeded` in the raw job log; grepped all 2,392 logs on
   Alvis to confirm exactly 8 total affected jobs sweep-wide (all seq12); retried and
   verified all fixed.

**Near-miss, caught and recovered**: an overly broad cleanup grep briefly deleted the
`original` baseline predictions for the same 6 spot-check sequences from the merged file —
their raw source data was already gone from Alvis (deleted in the initial quota-reclaim
pass), so the only recovery path was a local `.bak` file kept from an unrelated earlier
cleanup step. Recovered cleanly, but a reminder to keep more than one copy of large derived
artifacts once their raw source is gone.

Final state: `all_preds.txt` (711,348 lines) / `all_gts.txt` (35,456 lines), md5-verified
synced Alvis↔local, all 58 sequences uniformly covered (except the dataset-wide-disabled
`radar_noise_induced_shifts`). `compute_robustness.py` has not yet been run across the full
merged dataset — still only validated against the single seq46 pilot condition.

## Robustness visualization suite built (with two corrections along the way)

Built the 8-category visualization suite from `robustness-visualization-plan.md`
against `all_preds.txt` at 748,981 lines (grown since the morning session).
Precomputed artifacts the task brief pointed to didn't exist at their stated
path — rebuilt `row_table_iou{03,05}.parquet` and both `ap_robustness_local*.json`
from scratch via `ingest.py`/`run_ap_robustness.py`.

**First pass** flagged a survivorship-bias issue (naive pooled AP over
`radar/lidar_frame_deletion_*` gives mAP above baseline because those
conditions only have predictions for 0.2–4.0% of frames) and applied a
90%-coverage exclusion threshold. That threshold *also* wrongly caught
`lidar/radar_gaussian_noise_*`, which turned out to be a real bug in
`ingest.py`, not a coverage problem: a frame where the model genuinely
detects zero objects (a real `dummy` line) was silently dropped from the
row table instead of scoring as a full miss, because the matcher only
iterated over post-filter (non-dummy) prediction groups. Fixed
(`ingest.py`, tracks dummy-only frames separately, synthesizes FN rows for
them); gaussian_noise conditions now show 100% coverage and the corrected,
much starker number: `lidar_gaussian_noise_high` mAP=15.7 (was 33.5
pre-fix), a 77% relative drop — the clearest finding in the dataset. Also
standardized the whole report on IoU=0.3 (matches official K-Radar BEV
methodology) instead of the initial 0.5. New baseline: mAP=69.27.

**Second correction**: initially called item 7 (zero-sensor ablation) out
of scope, reasoning it needed new inference runs. User pushed back —
`radar_loss_complete_zero`/`lidar_loss_complete_zero`/`camera_loss_complete`
already zero-fill exactly one sensor's tensor while leaving the others
clean, i.e. they *are* the ablation, already in the sweep. Built it:
camera=0 → 100.7% mAP retention (no loss), radar=0 → 94.2%, lidar=0 →
58.3% — independently confirms the lidar-dominant story from a different
angle.
